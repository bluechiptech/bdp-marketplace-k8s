====================================================================
BDP PLATFORM — SETUP ON AN EXISTING KUBERNETES CLUSTER
====================================================================
Works for on-prem (kubeadm / RKE2 / k3s), EKS, GKE, or any conformant
cluster. Images are pulled from the vendor registry — TODAY that is
bdpmarketplace.azurecr.io (private; credentials in step 4a); once the
GHCR publish (scripts/release.sh) has run it can be
ghcr.io/bluechiptech instead. The cluster needs outbound internet.
For a fully offline cluster use the air-gap bundle's import-bundle.sh
instead — every step below stays the same except the values file
(values-airgap.yaml).

WHAT YOU NEED BEFORE STARTING
- kubectl + helm (>= 3.14) pointed at the cluster, cluster-admin
- a DNS name you control
- your signed license.key file (issued by Bluechip)
- pull credentials for the vendor registry (step 4a)

--------------------------------------------------------------------
STEP 0 — SINGLE-NODE CLUSTERS ONLY
--------------------------------------------------------------------
kubeadm taints the control plane so ordinary workloads won't schedule
on it. On a single-node cluster nothing would ever start. Check and
remove it:

    kubectl describe node | grep -i taint
    # if it shows node-role.kubernetes.io/control-plane:NoSchedule:
    kubectl taint nodes --all node-role.kubernetes.io/control-plane-

Also size-check the node: the platform (postgres, redis, keycloak,
22 services at 512Mi requests each, UI, prometheus, loki) fits on
8 CPU / 16 GB but it is snug — pods stuck Pending with "Insufficient
memory/cpu" mean the node is too small or requests need trimming.

On 16 GB nodes the Loki caches are the trap: the loki subchart
defaults request ~9 GB for its chunks/results caches alone, which
can deadlock the whole install (half the pods Pending, node at 99%
of its memory-request quota). The install command in 4c includes the
two --set flags that shrink them; do not omit them on small nodes.

--------------------------------------------------------------------
STEP 1 — CHECK STORAGE
--------------------------------------------------------------------
    kubectl get storageclass

- There must be a DEFAULT StorageClass (marked "(default)") —
  postgres, redis, keycloak, prometheus and loki create PVCs from it.
- Note whether any class supports ReadWriteMany (NFS, CephFS,
  Longhorn, EFS on AWS, Filestore on GKE). Used in step 4; if you
  have none, you will disable shared tool storage instead.
- NO StorageClass at all (fresh kubeadm cluster)? Install the
  local-path provisioner and mark it default:

    kubectl apply -f https://raw.githubusercontent.com/rancher/local-path-provisioner/v0.0.31/deploy/local-path-storage.yaml
    kubectl patch storageclass local-path \
      -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
    kubectl get storageclass    # must now show: local-path (default)

  local-path is RWO-only (no RWX), so in step 4 use
  --set sharedStorage.enabled=false.

--------------------------------------------------------------------
STEP 2 — INGRESS CONTROLLER
--------------------------------------------------------------------
First check whether one is already running:

    kubectl get ingressclass
    # any class listed = a controller is installed. The chart
    # expects class "nginx"; a different name (cloud-provider
    # controllers, RKE2's built-in, ...) also works — pass
    # --set global.ingressClassName=<name> in step 4c.

    kubectl get pods -A | grep -i ingress
    # the controller pod must be 1/1 Running

    kubectl get svc -A | grep -iE 'ingress.*LoadBalancer|LoadBalancer.*ingress'
    # note the EXTERNAL-IP — that is the <IP> for step 3. No
    # LoadBalancer service? The controller is in hostPort/NodePort
    # mode — use the node's public IP instead.

If all three check out, skip to step 3. Otherwise install
ingress-nginx:

    # Bare metal only, FIRST: install MetalLB with an address pool so
    # a LoadBalancer IP can be handed out.
    helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
    helm install ingress-nginx ingress-nginx/ingress-nginx \
      -n ingress-nginx --create-namespace
    kubectl get svc -n ingress-nginx ingress-nginx-controller
    # wait for EXTERNAL-IP

Single node (or no load balancer at all)? Skip MetalLB and bind the
controller directly to the node's ports 80/443 instead:

    helm install ingress-nginx ingress-nginx/ingress-nginx \
      -n ingress-nginx --create-namespace \
      --set controller.hostPort.enabled=true \
      --set controller.service.type=ClusterIP

    kubectl get pods -n ingress-nginx   # controller 1/1 Running
    curl -s -o /dev/null -w '%{http_code}\n' http://<node-public-ip>/
    # 404 = nginx is answering on the hostPort. In this mode there is
    # no EXTERNAL-IP — the node's public IP is your entry point (use
    # it in step 3). Check it from outside the node too, so you know
    # the provider firewall lets 80/443 in.

Do NOT add any Azure health-probe annotations — those are AKS-only.

--------------------------------------------------------------------
STEP 3 — DNS
--------------------------------------------------------------------
Point a wildcard at the EXTERNAL-IP (hostPort mode: the node's
public IP):

    *.bdp.yourcompany.com  ->  <IP>

No wildcard support? Two A records are enough:

    bdp.yourcompany.com           ->  <IP>
    keycloak.bdp.yourcompany.com  ->  <IP>

(Keycloak is served at keycloak.<domain> — without that second
record, login will fail.) Verify before installing:

    dig +short bdp.yourcompany.com
    dig +short keycloak.bdp.yourcompany.com
    # both must print the IP

For a quick test without DNS, use <ip>.sslip.io as the domain.

--------------------------------------------------------------------
STEP 4 — INSTALL
--------------------------------------------------------------------
    git clone https://github.com/bluechiptech/bdp-marketplace-k8s.git
    cd bdp-marketplace-k8s
    # already cloned earlier? run "git pull" — the vendored subcharts
    # were added to the repo on 2026-08-07; older clones lack them and
    # helm fails with "found in Chart.yaml, but missing in charts/".

The clone contains the COMPLETE chart, including the patched vendored
subcharts in charts/bdp/charts/. NEVER run "helm dependency build" —
it would replace those patched subcharts with unpatched upstream
copies and break the registry wiring.

4a. REGISTRY CREDENTIALS. The default values.yaml pulls every image,
    digest-pinned, from the vendor registry
    bdpmarketplace.azurecr.io, which is private. Get the registry
    username + password from the vendor (Bluechip internal:
    portal.azure.com -> container registry "bdpmarketplace" ->
    Access keys -> enable Admin user).

    The pull secret MUST be created with kubectl BEFORE the install —
    do NOT use global.registryCredentials.create=true here. The
    kube-prometheus-stack admission job is a PRE-INSTALL HOOK: it
    runs before the chart's manifests are applied, so a chart-created
    secret does not exist yet when the hook pod tries to pull, and
    the whole install wedges in ImagePullBackOff until the timeout.

    kubectl create namespace bdp --dry-run=client -o yaml | kubectl apply -f -
    kubectl create secret docker-registry bdp-registry-cred -n bdp \
      --docker-server=bdpmarketplace.azurecr.io \
      --docker-username='<registry-username>' \
      --docker-password='<registry-password>'

    Then create the values file that points the chart (and the loki/
    alloy subcharts, which use different keys) at that secret. Keep
    it in your HOME directory — outside the repo, so it can never be
    committed; it contains no credentials now, but the habit is the
    protection:

    cat > ~/pull-secrets.yaml <<'EOF'
    global:
      registryCredentials:
        create: false
      imagePullSecrets: [{name: bdp-registry-cred}]
    loki:
      imagePullSecrets: [{name: bdp-registry-cred}]
    alloy:
      global:
        image:
          pullSecrets: [{name: bdp-registry-cred}]
    EOF

4b. CERT-MANAGER CRDS (required when TLS mode is acme, step 5). The
    chart renders Certificate/Issuer resources, so the CRDs must
    exist BEFORE the install — and Helm must then be told it owns
    them, or it refuses with "invalid ownership metadata":

    kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.15.3/cert-manager.crds.yaml
    for crd in $(kubectl get crd -o name | grep cert-manager.io); do
      kubectl label   $crd app.kubernetes.io/managed-by=Helm --overwrite
      kubectl annotate $crd meta.helm.sh/release-name=bdp \
        meta.helm.sh/release-namespace=bdp --overwrite
    done

4c. INSTALL — the verified single-node invocation (hostPort ingress
    from step 2, local-path storage from step 1, Let's Encrypt TLS):

    helm install bdp charts/bdp -n bdp --create-namespace \
      -f ~/pull-secrets.yaml \
      --set global.externalDomain=bdp.yourcompany.com \
      --set sharedStorage.enabled=false \
      --set billing.mode=byol \
      --set global.tls.mode=acme \
      --set global.tlsSecretName=bdp-tls \
      --set global.adminEmail=you@yourcompany.com \
      --set loki.chunksCache.allocatedMemory=512 \
      --set loki.resultsCache.allocatedMemory=256

    The two loki lines shrink its caches from the ~9 GB the subchart
    defaults request down to 768 MB — required on a 16 GB node (see
    step 0), harmless headroom on bigger clusters (drop them if you
    have 32 GB+ and want the full log-query cache). On a 16 GB node
    also halve the per-service memory requests:
      --set serviceDefaults.resources.requests.memory=256Mi

    Deliberately NO --wait: helm applies everything and returns
    (after a short pause while the pre-install hooks run), then the
    cluster pulls several GB of images on its own — often longer
    than any sane --wait timeout on a first install. Watch progress
    with:

        kubectl get pods -n bdp -w

    Done when every pod is Running 1/1 (jobs: Completed).
    ContainerCreating for a long while = still downloading; only
    ImagePullBackOff or Pending are actual failures (see
    troubleshooting).

    - Cluster with an RWX-capable StorageClass? Replace the
      sharedStorage line with:
          --set sharedStorage.storageClass=<your-RWX-class>
    - A failed attempt can leave the release name in use; clear it
      with "helm uninstall bdp -n bdp" and re-run. The adopted
      cert-manager CRDs survive the uninstall (they carry
      helm.sh/resource-policy: keep); re-running step 4b anyway is
      harmless — it is idempotent.

ALTERNATIVE — GHCR, no Azure credentials (NOT YET AVAILABLE: requires
the vendor's GHCR publish, scripts/release.sh, to have run; until
then the package does not exist and helm returns 404 "name unknown"):

    helm install bdp oci://ghcr.io/bluechiptech/charts/bdp \
      -n bdp --create-namespace \
      -f charts/bdp/values-ghcr.yaml \
      <same --set flags as 4c>
    # private GHCR packages: helm registry login ghcr.io first, and
    # use registry ghcr.io + a read:packages token in pull-secrets.yaml

The install takes 10–20 minutes: postgres/redis/keycloak, the 22
platform services, the UI, the observability stack, and a seed job
that bootstraps the Keycloak realm.

--------------------------------------------------------------------
STEP 5 — TLS
--------------------------------------------------------------------
Default is plain HTTP until you give it a certificate. Pick one:

- Own certificate:
      kubectl create secret tls bdp-tls -n bdp --cert=... --key=...
  and add:  --set global.tlsSecretName=bdp-tls

- Let's Encrypt (domain must be publicly resolvable):
      --set global.tls.mode=acme \
      --set global.tlsSecretName=bdp-tls \
      --set global.adminEmail=you@yourcompany.com

- Throwaway test only:
      --set global.insecureSkipTlsVerify=true

--------------------------------------------------------------------
STEP 6 — LOG IN
--------------------------------------------------------------------
There is no default password. The post-install seed job generates
random passwords for the two seeded application users (admin and
engineer), sets them in Keycloak and stores them in the
bdp-credentials secret. Retrieve them with:

    # user "admin":
    kubectl get secret bdp-credentials -n bdp \
      -o jsonpath='{.data.admin-password}' | base64 -d; echo
    # user "engineer":
    kubectl get secret bdp-credentials -n bdp \
      -o jsonpath='{.data.engineer-password}' | base64 -d; echo

(The Keycloak admin-console superuser is separate: user "admin",
password in the bdp-keycloak secret, key admin-password.)

Browse to https://bdp.yourcompany.com and sign in.

If bdp-credentials is missing, the seed job failed after resetting
the Keycloak passwords — the generated passwords are lost. Fix the
cause (kubectl logs job/bdp-seed-<revision> -n bdp), then re-run the
seed, which regenerates and stores fresh passwords (the post-upgrade
hook recreates the job automatically):

    helm upgrade bdp ./charts/bdp -n bdp --reuse-values

NOTE: this cuts both ways — EVERY helm upgrade re-runs the seed and
ROTATES the admin/engineer passwords. After any upgrade, re-read
bdp-credentials before logging in; sessions already signed in keep
working.

--------------------------------------------------------------------
STEP 7 — ACTIVATE THE LICENSE
--------------------------------------------------------------------
Dashboard -> License -> Activate License: upload (or paste) your
license.key file, click Activate. The card shows organization, tier,
expiry date and a green ACTIVE badge. Until this is done,
billing.mode=byol intentionally blocks provisioning of data tools.

Renewal / tier upgrade: same flow with the new license.key file.

--------------------------------------------------------------------
STEP 8 — VERIFY
--------------------------------------------------------------------
    kubectl get pods -n bdp        # everything Running/Completed

    # every image should come from ghcr.io:
    kubectl get pods -n bdp -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' \
      | cut -d/ -f1 | sort | uniq -c

Then provision a tool from the UI catalog (e.g. ClickHouse) — it
should pull its chart and images from GHCR too.

WORKED EXAMPLE — THE VERIFIED MTN INSTALL (2026-08)
--------------------------------------------------------------------
Every placeholder above, with the real values of the reference
install this guide was verified against (single kubeadm v1.35 node
"ag-2222-mtn-cloud-mk8s-m-1", 8 CPU / 16 GB, hostPort ingress):

    <IP> / node public IP        102.89.90.152
    bdp.yourcompany.com          mtnbdp.bluechiptech.biz
    keycloak.bdp.yourcompany.com keycloak.mtnbdp.bluechiptech.biz
    DNS                          two A records -> 102.89.90.152
    registry                     bdpmarketplace.azurecr.io
                                 (secret bdp-registry-cred, ns bdp)
    StorageClass                 local-path (default), RWO-only
    you@yourcompany.com          agbadeyanka@bluechiptech.biz

The exact install command (helm get values bdp -n bdp reproduces
this list from the live release):

    helm install bdp charts/bdp -n bdp --create-namespace \
      -f ~/pull-secrets.yaml \
      --set global.externalDomain=mtnbdp.bluechiptech.biz \
      --set sharedStorage.enabled=false \
      --set billing.mode=byol \
      --set global.tls.mode=acme \
      --set global.tlsSecretName=bdp-tls \
      --set global.adminEmail=agbadeyanka@bluechiptech.biz \
      --set loki.chunksCache.allocatedMemory=512 \
      --set loki.resultsCache.allocatedMemory=256 \
      --set serviceDefaults.resources.requests.memory=256Mi

    (The last line halves every platform service's memory request
    from the 512Mi default — together with the loki lines this is
    what makes the stack fit a 16 GB node.)

Post-install fixes this environment needed, both covered in
TROUBLESHOOTING below:
  - CoreDNS NXDOMAIN server block for the node's DHCP search domain
    cloud-1.ict.mtn.com.ng (MTN's resolvers answer NOERROR for
    anything under it, which breaks all external DNS in musl pods).
  - One-time Keycloak/bdp-credentials password re-sync after a
    partially failed seed run (fixed in the seed image going
    forward).

WHAT THIS PROCEDURE INSTALLS ON THE CLUSTER
--------------------------------------------------------------------
Inventory of everything the steps above leave behind (useful for
audits and teardown):

    local-path-provisioner        ns local-path-storage; StorageClass
                                  "local-path" marked default (step 1)
    ingress-nginx                 helm release "ingress-nginx", ns
                                  ingress-nginx; hostPort 80/443 on
                                  the node in single-node mode (step 2)
    cert-manager CRDs v1.15.3     cluster-scoped, kubectl-applied and
                                  Helm-adopted into release bdp (4b)
    secret bdp-registry-cred      ns bdp; registry pull credentials,
                                  created manually with kubectl (4a)
    helm release "bdp"            ns bdp: postgres, redis, keycloak,
                                  cert-manager, the 22 platform
                                  services + UI + seed job, prometheus
                                  stack, loki, alloy, kserve CRDs
    Let's Encrypt account + cert  Issuer bdp-acme / Certificate
                                  bdp-tls in ns bdp (acme mode only)

Teardown (validated by a full uninstall/re-install cycle): helm
uninstall bdp -n bdp removes the release but KEEPS the cert-manager
CRDs and the bdp-platform-secrets secret (helm.sh/resource-policy:
keep); for a truly clean slate also "kubectl delete namespace bdp"
(this wipes ALL platform data, the pull secret and the issued
certificate — back the pull secret up first if you no longer have
the registry password). The ingress controller and storage
provisioner are yours to keep or delete separately.

TROUBLESHOOTING
--------------------------------------------------------------------
- "no matches for kind Certificate / Issuer ... ensure CRDs are
  installed first" at install time
    step 4b was skipped — apply the cert-manager CRDs first.
- CustomResourceDefinition "... cert-manager.io" exists and cannot
  be imported into the current release: invalid ownership metadata
    the CRDs exist but were never adopted by Helm — run the
    label/annotate loop in step 4b, then re-run the install.
- Install stalls ~20m then STATUS: failed; only ONE pod exists
  (…admission-create…) in ImagePullBackOff; events show
  "FailedToRetrieveImagePullSecret … (bdp-registry-cred)"
    the pull secret didn't exist when the pre-install hook ran —
    it must be created with kubectl BEFORE the install (step 4a),
    not by the chart. helm uninstall, create the secret, re-run.
- ImagePullBackOff with "401 Unauthorized" AFTER the secret exists
    the registry credentials themselves are wrong — re-check the
    username/password (Admin user enabled? password copied whole?)
    and recreate the secret.
- ImagePullBackOff (other)
    registry unreachable from the nodes — check egress rules
    (ports section below).
- TLS certificate stuck READY:False; cm-acme-http-solver-* pods in
  ImagePullBackOff
    charts from 2026-08-08 set imagePullSecrets on the solver pod
    template automatically — on older charts the solver pods run
    under the namespace's DEFAULT ServiceAccount, which does not
    reference the pull secret. Attach it and let cert-manager
    recreate the solvers:
      kubectl patch serviceaccount default -n bdp \
        -p '{"imagePullSecrets":[{"name":"bdp-registry-cred"}]}'
      kubectl delete pods -n bdp -l acme.cert-manager.io/http01-solver=true
    (Also check DNS first: with acme mode BOTH records from step 3
    must resolve publicly, or the challenge can never be reached.)
- Login redirect fails / UI cannot reach Keycloak
    your load balancer doesn't hairpin — common in hostPort mode,
    where pods often cannot reach the node's own PUBLIC IP from
    inside (NAT doesn't loop back). Set:
      --set global.keycloakHostAliasIp=<ClusterIP of the
        ingress-nginx-controller Service>
    and helm upgrade.
- /login?...&error=OAuthSignin, UI logs show
  "getaddrinfo ENOTFOUND keycloak.<domain>" although the name
  resolves fine from the node
    pods inherit the node's DHCP search domain (check
    "search ..." in a pod's /etc/resolv.conf). If the ISP/cloud
    resolvers answer <anything>.<that-search-domain> with NOERROR
    instead of NXDOMAIN, musl-based images (Alpine/Node) stop at
    that empty answer and never try the bare public name — ALL
    external DNS fails in pods while cluster names work. Fix in
    CoreDNS: add a server block ABOVE ".:53" in the coredns
    ConfigMap (kube-system) answering that zone authoritatively:
        <search-domain>:53 {
            errors
            template ANY ANY {
                rcode NXDOMAIN
            }
        }
    then: kubectl -n kube-system rollout restart deploy/coredns
- Cluster pages (Nodes/Resources/Pods/Namespaces) all 502 with
  {"code":"CM-0040","message":"Cluster registry kubeconfig fetch
  failed ... ResourceAccessException"} — or 500 "... is forbidden:
  User system:serviceaccount:bdp:default cannot list ..."
    chart older than 2026-08-08: bdp-cluster-manager was missing its
    BDP_CLUSTER_REGISTRY_URL env (fell back to 127.0.0.1:7018, the
    VM layout) and its ServiceAccount + RBAC. git pull and
    helm upgrade with the current chart (mind the password-rotation
    note in step 6).
- Login page loads but the seeded admin/engineer passwords from
  bdp-credentials are rejected ("Invalid user credentials")
    a seed run reset the Keycloak passwords but failed before (or
    while) publishing them — Keycloak and the secret are out of
    sync. Re-sync WITHOUT re-running the seed: take the Keycloak
    superuser password (secret bdp-keycloak, key admin-password),
    get an admin token from realm master (client_id=admin-cli),
    and PUT /admin/realms/bdp/users/<uid>/reset-password for admin
    and engineer with the values from bdp-credentials. (Or simply
    re-run the seed via helm upgrade --reuse-values, which
    regenerates both sides.)
- PVCs Pending
    no default StorageClass, or a storage class was set to "" (never
    do that — an empty string disables dynamic provisioning).
- Shared-storage PVC Pending
    the class you supplied is not actually RWX-capable.

--------------------------------------------------------------------
PORTS THAT MUST BE OPENED
--------------------------------------------------------------------
Inbound from users (perimeter firewall -> load balancer) — the ONLY
externally opened ports; everything is routed through the ingress:
    443/TCP   UI, API (/api), Grafana (/grafana), Keycloak
              (keycloak.<domain>)
    80/TCP    HTTP->HTTPS redirect; REQUIRED for Let's Encrypt
              HTTP-01 if global.tls.mode=acme

Outbound from cluster nodes (egress):
    bdpmarketplace.azurecr.io (+ *.blob.core.windows.net) : 443
              (image pulls — default/ACR installs)
    ghcr.io + pkg-containers.githubusercontent.com : 443
              (image/chart pulls — GHCR installs, once published)
    acme-v02.api.letsencrypt.org : 443   (only if TLS mode is acme)
    <local registry port>                (air-gapped installs; no
                                          other egress needed)
    BYOL licensing phones home to NOTHING — fully offline.

Node-to-node (only if you firewall between cluster nodes):
    9100/TCP  node-exporter (runs hostNetwork: true; Prometheus
              scrapes it on the node IP)
    plus your cluster's normal Kubernetes/CNI ports (already open on
    a working cluster: API 6443, kubelet 10250, CNI overlay ports).

Pod-network internal only — no firewall rules needed; listed for
NetworkPolicy authors: platform services 7000-7023, UI 3000,
PostgreSQL 5432, Redis 6379, Keycloak 80, Loki 3100, Prometheus 9090,
Alertmanager 9093.
